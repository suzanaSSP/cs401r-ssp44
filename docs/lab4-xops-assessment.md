## Pipeline Stage Mapping
- Phase 1: Source & Triggering
    - Pulls code from Github when main is pushed using CodeStar connection
    - Extracts COMMIT_SHA
    - RATIONALE: Ensures every build is strictly traceable to a specific commit in version control to be able to reproduce later if needed

- Phase 2: Environment Provising & Dependency Isolation
    - Install necessary libraries from requirements.txt
    - Resolves AWS account & S3 buckets
    - RATIONALE: Updates environments so model and tests can run properly

- Phase 3: Pre-Flight Data & Feature Validation
    - Executes tests for test_data and test_features against S3 dadta
    - Fails for any failed test
    - This is CodeBuild: PRE_BUILD Phase
    - RATIONALE: Validates data is properly cleaned and featured so it doesn't change the model's training. It saves compute cost, if there is an error in the data it halts the building proccess

- Phase 4: Continuos Model Training
    - CodeBuild: Build/ Sagemaker Pipeline
    - Trains model using *northstar-churn-pipeline* 
    - RATIONALE: Training spot instances is less cost and automatically captures training metrics and model artifacts

- Phase 5: Model Quality Gating
    - CodeBuild: BUILD + POST_BUILD/ CodePipeline: Manual Approval
    - Evaluates metrics for trained model
    - Runs test_model.py
    - Models that pass wait for approvel in PendingManualApproval. Someone has to go and approve. 
    - RATIONALE: Running tests on model prevents model regression. PendingManualApproval enforces human-in-the-loop before models can ever serve production to ensure there isn't any other problems not captured by the tests. 

## Champion-Challenger
- **Role Definition**:
    - **Champion**: The currently approved, production model package in the SageMaker Model Registry (`ModelApprovalStatus: Approved`, e.g., Version 11) serving production inferences.
    - **Challenger**: The newly trained candidate model package registered by the SageMaker Pipeline (`ModelApprovalStatus: PendingManualApproval`, e.g., Version 13) generated by the CI build.
- **Numeric & Binary Decision Criteria**:
    - The champion-challenger gate is strictly **binary** (Pass = 1 / Fail = 0). If the candidate passes all checks, it remains in `PendingManualApproval` for human verification and deployment; if it fails any check, CodeBuild terminates with exit code 1, and the `post_build` phase automatically updates the Model Registry package to `Rejected`.
    - **Primary Regression Gate (Numeric Threshold)**:
      $$\text{Candidate AUC-ROC} \ge \text{Champion AUC-ROC} - 0.02$$
      Implemented in `tests/test_model.py::test_regression_check`. The candidate model's AUC cannot drop by more than 0.02 (200 basis points) compared to the current approved Champion.
    - **Statistical Significance Lift Gate (Numeric Threshold)**:
      $$\text{lift\_ci\_low} > 0.0$$
      Implemented in `tests/test_model.py::test_model_beats_baseline`. The 95% bootstrap confidence interval lower bound of AUC lift over the recency-only baseline must strictly exceed 0. A candidate cannot be promoted on a point estimate alone because sample variance could show false lift; the entire confidence interval must exclude zero.
    - **Operational Metric Thresholds**:
      - $\text{Precision@Top10} \ge 0.65$ (`test_precision_top10_meets_threshold`)
      - $\text{Recall@Top10} \ge 0.25$ (`test_recall_top10_meets_threshold`)
      - Validation churn rate: $0.15 \le \text{positive\_rate\_val} \le 0.30$ (`test_positive_rate_is_realistic`)
- **Why a Numeric & Binary Rule is Required**:
    - Qualitative criteria such as "if the model is better" are subjective, non-deterministic, and cannot be evaluated in automated CI/CD gating.
    - A candidate could have a slight point-estimate AUC lift (+0.005) purely due to split noise, but suffer catastrophic regression on key business slices. Enforcing concrete numeric thresholds ($\ge \text{Champion} - 0.02$ and $\text{lift\_ci\_low} > 0.0$) guarantees reproducible, deterministic quality gates without human bias.

## Retraining Triggers
Two automatable retraining triggers are defined for the NorthStar churn prediction system (scheduled and metric/drift-driven):

### 1. Scheduled / Cadence-Based Retraining
- **Objective**: Ingest new customer transaction data, update feature aggregations, and adapt to regular seasonality or long-term trends before data becomes stale.
- **Schedule Expression**:
  - `cron(0 2 ? * SUN *)` (Every Sunday at 02:00 UTC) / `rate(7 days)`.
- **AWS Service**: **Amazon EventBridge Scheduler**.
- **Execution Mechanism**:
  - An EventBridge rule evaluates the cron schedule and triggers **AWS CodePipeline** (`northstar-pipeline`) via `codepipeline:StartPipelineExecution`.
  - The pipeline automatically runs pre-build data validation, triggers SageMaker Pipeline training with the updated feature store snapshot, validates the model against the Champion, and registers a new version for approval.

### 2. Event-Driven / Metric & Drift-Based Retraining
- **Objective**: Immediately trigger retraining when customer behavior shifts significantly (feature drift) or when model predictive accuracy degrades in production.
- **AWS Services**: **Amazon SageMaker Model Monitor** $\rightarrow$ **Amazon CloudWatch Alarm** $\rightarrow$ **Amazon EventBridge**.
- **Specific Numeric Thresholds**:
  - **Feature / Data Drift**: Population Stability Index ($\text{PSI}) \ge 0.25$ (or Kolmogorov-Smirnov test $p$-value $< 0.05$) on key model features (such as `days_since_last_purchase`, `total_spend_90d`, `purchase_frequency_30d`) compared against baseline constraints.
  - **Model Performance Degradation**: Production ground-truth churn AUC-ROC $< 0.72$ (or Precision@Top10 $< 0.60$) calculated across a rolling 7-day monitoring window.
- **Execution Mechanism**:
  - SageMaker Model Monitor analyzes live endpoint requests against the training baseline and publishes drift metrics to Amazon CloudWatch.
  - A **CloudWatch Alarm** monitoring `ModelMonitorDriftDetected` (or `ProductionAUC < 0.72`) enters the `ALARM` state.
  - The alarm state transition triggers an **Amazon EventBridge** rule that invokes `codepipeline:StartPipelineExecution` on `northstar-pipeline`, initiating an automated retrain and champion-challenger evaluation.

The Machine Learning Operations is at level 2 because it has a script that automatically runs tests and the building process. When code is pushed, there’s a manual run to run tests on the data (DataOps); after data is ready, it builds and trains the model. After training the model, test_model.py script runs automatically to test the model’s metrics, performance, etc. After all the tests passed, there is a manual approval to have the model pass through if it exceeds the Champion model. This prevents model regression. Though the building, testing, and post build process is all automatic, there are still human-in-the-loop components like the Manual Approval in the middle of the pipeline. There is also a manual run to start this process. 

**Gap to Level 3: [What is the specific missing capability?]**

Similar to DataOpa, what’s missing is an automation to detect when code has been pushed and automatically run all of this process. Additionally, the current process lacks a performance-based retraining trigger, where a system actively monitors the model's live predictive quality and automatically launches a retraining pipeline whenever performance drops below an acceptable threshold.

**Top priority investment: [One concrete change that would advance maturity]**

Configure an EventBridge rule connected to CloudWatch metric alarms that monitors model performance and automatically retrains it and runs tests when its AUC reaches below its threshold.
