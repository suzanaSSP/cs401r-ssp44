## ADR-001: NorthStar Platform Foundation

### Status
Accepted

### Context
[What is NorthStar building? Why does a shared AI platform need an identity model
and a storage tier structure from day one?]

NorthStar is building three complex AI systems, a churn prediction model, Offer Generation, and Customer Service Agent, that require an AI platform from day one because of the security, storage, and performance. 
To protect customer records from internet exposure, creating S3 buckets, and IAM roles with policies where only specific engineers have access to this data is necessary. It is also important to develop this from the start to ensure that customer data is protected throughout the whole development process and avoid risking leaking data. 
Additionally, because Northstar is a growing company, they need a service that is easily able to scale data storage as customer records increase, which is why AWS S3 is a top choice.
Finally, establishing a unified AI platform from the outset ensures these three workloads can scale reliably and securely.

### Decision
[Describe the VPC topology, S3 prefix design, and IAM role model you built.
Every rationale must tie to a NorthStar requirement — not "best practice."]
VPC -> 
The VPC has isolated private subnets distributed across multiple availability zones. It doesn’t have direct access to the internet, only through an internet gateway. Training, processing, and database instances remain entirely isolated from the public internet, protecting customer data privacy from external exposure. Internal communication between SageMaker, S3 and platform services are routed privately across AWS PrivateLink and Gateway VPC endpoints, ensuring customer records never traverse the public web.

S3 -> 
The S3 buckets go from raw to processed to features to artifacts. The raw bucket is for the unprocessed raw customer data as it arrives. After being cleaned, validated, and normalized for transformation, it goes to the processed bucket. After it’s transformed for model training it goes to the features bucket. The artifacts are reserved for model outputs generated by SageMaker training and tuning jobs. Having the data separated in these jobs provides for a more clean and smooth training process. If there is something from the features or processes that needs to change, there is the raw data to go back to. 

IAM Role -> 
The only person with access to IAM roles is the ML Engineer. Because the ML Engineer is the one building these platforms, the engineer needs access to build it. Right now, only the ML Engineer has access to these things. If too many people have access to the AWS services for the company, especially those that aren’t involved in the building, it could lead to casual mistakes and confusion. 

### Consequences
#### What this makes easy
Spread out access: Restricting IAM roles to specific S3 prefixes prevents contamination from cross-pipelines and ensures strict governance over customer data from 400 retail stores. 
Deterministic Pipeline and debugging: having immutable data in raw/ then versioning model binaries in artifacts/ makes so that reproducing training runs is possible. Additionally, having the process split this way makes it simple to trace pipeline failures and audit model behavior
Safe Experimentation: ML Engineers can iterate and train models in isolated private subnets without exposing private customer data to the public internet or risk accidentally deletion or leaking of source data.  

#### What this makes harder
Having such a structured pipeline can increase the time it takes for a new engineer to learn and work with this platform. Engineers cannot simply dump files into a single shared bucket or access instances directly over the public internet. Every interaction requires properly scoped IAM permissions and AWS PrivateLink/VPC endpoints.
Moving data across four different lifecycle stages (raw to processed to features to artifacts) can create overhead and requires automated ETL jobs (AWS Glue, SageMaker Processing)  rather than quick scripts.
#### What would cause you to revisit this decision
If the store continues to grow and expand internationally, data residency laws might mandate to keep regional store data isolated in separate AWS accounts/regions rather than prefix-isolated buckets in a single VPC. 

### Alternative Considered
[One genuinely different approach and why you rejected it]
One alternative would be to provision separate AWS accounts or distinct VPCs connected via AWS Transit Gateway for each of the three workloads (one for Churn Prediction, one for Personalized Offers, and one for the Customer Service Agent), each with independent S3 data buckets.
Why it was rejected:
At NorthStar’s current scale, managing cross-account IAM trust relationships, Transit Gateway attachments, and duplicate infrastructure automation significantly slows iteration without meaningful security gain.
The churn, offer generation, and agent models all consume the same foundational 400-store POS and customer profiles. Splitting buckets across accounts would require complex cross-account S3 replication, inflating cloud storage and egress costs.
Standard IAM policy boundaries combined with path-based prefix separation and private VPC subnets already achieve strict workload and environment isolation without the administrative tax of a multi-account organization.
### AWS Service Selection
- Networking isolation model
	- Amazon VPC: Isolated private subnet distributed across multiple Availability Zones with no direct route to an internet gateway for ML training.

- Storage design
	- Amazon S3: Unified bucket with strict prefixes (raw, processed, features, artifacts)  Default (SSE-KMS) with CMK enforcing data privacy across stores. Bucket policies and IAM condition keys restrict write access to raw. 

- Identity model
	- AWS IAM and SageMaker Execution Roles: Execution roles for processing and training jobs are scoped strictly to their respective S3 prefixes (e.g., training jobs have read-only access to features and write-only access to artifacts/models/<workload>/), preventing unintended cross-pipeline data tampering.

- ML development environment
	- Amazon SageMaker Studio: Disables direct internet access from user notebooks, requiring all dependency installations, data queries, and API calls to route through vetted internal network paths and VPC endpoints.
